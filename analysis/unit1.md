# Unit 1 Analysis 
## Modelling justification

The schema was made around one asymmetry: `passengers`, `flights`, and `airports` are reference data that changes slowly, while `bookings` is a high-volume, append-heavy fact table that changes constantly. 

**Primary keys.** `passengers`, `flights`, and `bookings` all use surrogate integer identity keys rather than any "natural" identifier. For `bookings` there is no natural candidate key at all. For `passengers`, a natural key was tempting (email, or passport number), but both are mutable-in-practice: emails get reissued, and passport numbers change when a passport is renewed or a country changes its numbering scheme. Using a surrogate key, enforcing `passport_number` and `email` as separate `UNIQUE` constraints gets the uniqueness guarantee without tying the row's identity to a value that can legitimately change over a passenger's lifetime. `airports`, by contrast, uses the IATA airport code as a natural primary key. That code is externally standardized, and already the value every join and every human-readable report would want to display, adding a surrogate key on top would just be an extra join for no benefit.

**`ON DELETE` behavior.** The two foreign keys into `bookings` (from `passengers` and from `flights`) are both `RESTRICT`. This was the single most important decision in the schema: bookings are financial and legal records, and once one exists, neither the passenger nor the flight it references should be deletable out from under it. Instead, the two "producer-side" states that would normally tempt a hard delete, a passenger closing their account, a flight being pulled from the schedule are modeled as data changes (an anonymization routine at the application layer, and the `flights.is_active` flag) rather than row deletions. The `flight_routes` junction table is the one place `CASCADE` is used, specifically because a route leg is meaningless without its flight,  once a flight itself is genuinely removable its route rows should go with it automatically rather than requiring a second manual delete.

**Rules enforced in the schema vs. left to the application.** Everything expressible is a simple, single-row condition was pushed into the schema as a `CHECK` constraint... a flight's arrival must be after its departure, `booking_status` and `loyalty_tier` are restricted to a fixed enumeration. These are cheap to enforce and impossible to accidentally bypass once they live in the database rather than in every piece of application code that touches the table. What was left to the application layer is any rule that requires reasoning across multiple rows or tables for example, preventing a passenger from being double-booked on two overlapping flight. PostgreSQL can express some of these with `EXCLUDE` constraints and extensions, but doing so here would add real complexity for a rule that the booking workflow already has to check anyway and getting it right is easier to reason about, test, and evolve in application code than in a constraint that would need to be rewritten every time the business rule changes.

## Reflection

The decision that I think would be different based on a different designer’s possible approach is my decision to use a surrogate key (`passenger_id`) for passengers instead of the actual passport number, which could serve as the primary key. A designer aiming solely for simplicity in reading may argue that the passport number is a unique identifier in the real world and that, because of that, using it as the primary key would allow any query against `bookings` to be performed without having to perform any lookups to get the correct passport information since the passenger would be able to provide the correct number over the phone.  

The reason I decided on the surrogate key is that I think the more relevant consideration in my decision is not only the read operations but also the write operations I anticipate for this database over time. The re-issue of passport numbers when the passengers renew their passports, combined with the occasional typo or corrected passport number that the passenger gives the airline that is not correct at the time but becomes correct later, could make it problematic if `passport_number` serves as the primary key. When this happens and `passport_number` serves as the primary key, the airline then has to go back and update every foreign key in the `bookings` table that points to the original `passport_number` value that now must be changed, and this cascade of changes could take a long time. Since `passenger_id` serves as the primary key, the company only needs to perform an `UPDATE` against the `passengers` table, since no foreign key `passport_number` needs to be changed.
